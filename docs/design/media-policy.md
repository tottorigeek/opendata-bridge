# 画像・メディアの扱い — ホスティングしないという決定

最終更新: 2026-09-03 / 状態: **決定**

OpenData Bridge は**画像バイナリを保持しない**。画像は CSV の列に入った
**URL 文字列としてのみ**流通させる。本書はその決定と、決定を覆す条件を記録する。

---

## 1. 決定

| 項目 | 決定 |
| --- | --- |
| 画像バイナリの保存 | **しない** |
| 画像専用のデータモデル | **作らない**(`Dataset` は表形式のまま) |
| 画像用の公開バケット | **作らない** |
| 画像 URL | CSV の通常の列値として、加工せずそのまま通す |
| リポジトリ | **分けない**(そもそも画像機能を作らないため論点が消える) |

## 2. なぜこの結論になったか

### 2-1. この領域の画像は、独立した資産ではなく「行に付属するもの」

実際に接続している 2 系統がどちらもそうだった。

- 政府標準オープンデータ形式(推奨データセット「イベント情報」)には `画像` 列があり、値は URL
- モバイルオーダー側の `radish_menus.image_url` も URL

つまり画像は既に「どこかにホストされていて、行がそれを指している」状態で存在する。
画像バンクを作らなくても、行を配れば画像は繋がる。

### 2-2. ホスティングは現在のストレージ設計と正面から衝突する

[`lib/storage.ts`](../../lib/storage.ts) は**非公開バケット + 署名 URL を使わず
アプリの認可済みルート経由で配信**という方針を明示的に選んでいる。
一方、画像は他サイトから `<img src>` で直接引かれる**公開 CDN URL** が要る。
同じドライバに相乗りさせられないので、公開バケットを別に立てることになる。
得られるものに対して、増える運用面が大きい。

### 2-3. 本当のコストはストレージではなく権利処理

CSV と画像で決定的に違うのはここで、コードの置き場所では解決しない。

- **CC-BY はクレジット表示が条件**。画像では表示位置まで問題になる
- **肖像権・施設管理権はどの CC ライセンスもカバーしない**。
  「CC-BY で公開されている」ことは「写っている人が同意している」ことを意味しない
- したがって 1 点ずつの目視レビューが要る。CSV にはない恒常的な人的コスト

ホスティングを始めるということは、この審査を自前で回すということである。

## 3. 代わりに提供するもの — 出典を本体と一緒に流す

画像を持たない代わりに、**複製する側が帰属表示を失わない**ようにする責任を負う。

`GET /api/v1/datasets/{id}/data` の応答に `source` を同梱する
(組織名 / データセット名 / ライセンス / `licenseUnresolved`)。
`format=csv` では `X-Dataset-*` ヘッダーで返す。詳細は [docs/api.md](../api.md)。

メタデータを別途取得しないと帰属が組み立てられない状態だと、
バッチごとに本体だけを叩く実装でクレジットが落ちるため。

### 3-1. 取り込み側(複製する側)の前提

画像 URL をミラーする利用者がいることを前提にする。トットリングの
イベント取り込みは実際にサーバー側で画像を取得して自前ストレージへ複製している。

流す画像 URL が満たすべき条件(取り込み側の実装から確定):

1. 認証なしで GET できる公開 URL
2. `http(s)` の直リンク(Google Drive の共有ページ等は不可)
3. 5MB 以内

**ホットリンクは参照だが、ミラーは複製・再配布であり、ライセンス条件は複製側が負う。**
この点は [docs/api.md](../api.md) に注意書きとして明記した。

## 4. 決定を覆す条件

以下が起きたら再検討する。**それまでは作らない。**

- **自治体が「置き場所のない写真」を渡してきたとき。** 現状の画像はすべて既に
  どこかにホストされているが、ホスティング先を持たない提供者が現れたら前提が崩れる
- 画像が別のデプロイ形態(エッジ / CDN、別のスケール特性)を要求するようになったとき

## 5. もしホスティングを作ることになったら

**リポジトリは分けない。** 組織・本人確認・ライセンス解決・カタログ検索・
地域マスタ・修正リクエスト・通知は CSV 側と共通で、これを二重管理するコストのほうが
「管理対象が異なる」コストより確実に大きい。代わりに 1 リポジトリ内で 3 箇所に線を引く。

1. **DB モデルを分ける** — `Dataset` は `columnsJson` / `rowCount` / `versions` /
   `lineage` と徹底的に表形式前提。画像を `rowCount: 0` の `Dataset` にすると
   マージウィザードにも一致率計算にも紛れ込む
2. **バケットを分ける** — §2-2 のとおり、非公開 + アプリ経由配信の方針と衝突するため
3. **`lib/assets/` は `lib/merge/` に触らせない** — 正規化・キー一致率・相性チェックは
   画像に対して意味を持たない

### 5-1. AGPL リポジトリに画像バイナリを置かないこと

「オープンだから一緒に」で画像を本リポジトリに commit しない。
**画像は OSS ではなくオープンライセンス素材**であり、AGPL はソースコード向けである。
仮に置く場合も `NOTICE` での個別のライセンス明記が必要になる。
