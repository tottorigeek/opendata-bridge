# マージ設計メモ — マージ型・相性チェック・来歴・バージョン

最終更新: 2026-08-13 / 状態: **設計確定・未実装**(決定事項は §7-1)

本書は、マージエンジンを「単に 2 つの CSV を結合する機能」から
「**出典を保持したまま、再現可能な形でデータを組み合わせる基盤**」へ拡張するための設計記録である。
実装済みの挙動と、これから決めることを区別して書く。

現在の実装は [`lib/merge/engine.ts`](../../lib/merge/engine.ts) と
[`app/api/merge/execute/route.ts`](../../app/api/merge/execute/route.ts) にある。

---

## 1. マージ型を 2 種に分ける

### 1-1. 方針

**「どの行が残るか」を名前で明言した 2 種**に絞る。
どちらも「エンジンが確実に提供できること」だけを名前で約束する。

| 型 | SQL | 残る行 | 利用者に示す問い |
| --- | --- | --- | --- |
| **項目拡張型** | LEFT JOIN | 手元(A)の行は**全部残る** | 「手元のデータに、別のデータの項目を足したい」 |
| **共通抽出型** | INNER JOIN | **両方にある行だけ** | 「両方に存在するものだけを取り出したい」 |

「項目」は**列**を指す。どちらの型でも列は増えるが、**行が変わらないのは項目拡張型だけ**である。
この違いが両者を分ける唯一の軸であり、名前もそこを指している。

型を選べば結合種別が決まるため、**`inner / left / full` という選択肢を UI から消せる**。
利用者が覚える概念が「型」ひとつになり、これらが利用者の語彙でないという問題も同時に解消する。

### 1-2. FULL OUTER を型に含めない理由

当初は完全外部結合を 3 つ目の型(照合型 / 全件統合型)にする案を検討したが、**採らない**。

現在のエンジンで完全外部結合を実行すると、
[`buildRow`](../../lib/merge/engine.ts) が片側 null の行を空文字で埋めるため、

- マッチした行 … 両方の情報が揃う
- A にしか無い行 … B 側の列がすべて空
- B にしか無い行 … A 側の列がすべて空

という**穴だらけの横長の表**になる。これは A の一覧でも B の一覧でもなく、
カタログに公開するデータセットとしての用途が想定できない。

さらに、人が「2 つを統合したい」と言うときに実際に欲しいのは、
**同種の 2 つの台帳を 1 本のきれいなリストにする**こと(県の施設台帳 + 市の施設台帳 → 重複を除いた施設一覧)である。
これには**列の対応付け**(県の「施設名」= 市の「名称」を同じ列に寄せる)と**重複排除**が必要で、
現在のエンジンはどちらも行わず、列を横に並べるだけである。
したがって「統合型」と名付けると**エンジンが提供できないものを名前で約束してしまう**。

完全外部結合の値打ちは「どちらにしか無いか」を**すべて見られる**ことにあり、
これは公開するデータセットではなく**診断**の材料である。§2-4 の相性チェックの計算基盤として位置づける。

> 真の統合(名寄せして 1 本化)は現エンジンに無い機能であり、**将来の別機能**として検討する価値がある。

### 1-3. 指標は両側算出し、解釈を型で変える

カバー率は**型によらず常に両側とも算出する**。型によって変えるのは
「どちらを主指標として前面に出すか」と、**同じ数値をどう解釈するか**である。

| | 項目拡張型 | 共通抽出型 |
| --- | --- | --- |
| 基準データ | A を明示的に選ばせる | 対等(基準なし) |
| 主指標 | A 側カバー率 | 両側カバー率 + Jaccard 係数 |
| 重要な副指標 | **多重度分布**(1 行が何件にマッチしたか) | 片側カバー率の偏り |
| 参考値(警告にしない) | B 側カバー率 | — |
| 想定出力行数 | ほぼ A の行数 | マッチした分のみ |

項目拡張型では、参照側(B)が基準側(A)より大きいのが通常であり、
**B 側カバー率が極端に低いことは正常な姿**である
(避難所 20 件に全国マスタを突き合わせれば B 側は 1% 未満になる)。
したがって項目拡張型では B 側カバー率を参考値として表示するにとどめ、
**警告や品質ゲートの対象にしてはならない**。問題でないものに警告を出すと、
利用者は直す必要のないものを直そうとする。

一方、共通抽出型で片側だけカバー率が極端に低いことは「集合がずれている」という明確な異常である。
**同じ数値が、一方では正常、他方では異常を意味する。**

項目拡張型で B 側カバー率より重要なのは**多重度**である。1 件の A 行が B の複数行にマッチすると、
出力が膨張するうえ「どの値を採用するのか」が定まらず、拡張という目的そのものが破綻する。

> なお、項目拡張型で方向(基準側と参照側)が生じること自体は直すべき歪みではなく、
> 「手元のデータを充実させる」という用途に内在する意味論である。
> 現在の実装が居心地悪いのは非対称だからではなく、**方向を宣言しないまま
> 選択順で暗黙に基準を決めている**ためである。型を選ばせて基準を明示すれば、
> 非対称性は解消すべき対象ではなく、宣言された前提になる。

## 2. 品質指標

### 2-1. 現在の定義と限界

```
マッチ率 = (B 側に 1 件以上マッチした A の行数) / (A の総行数)
```

限界が 4 つある。

1. **片側のみ。** B 側のカバー率は計算していない。A=20 行・B=10,000 行で 8 行マッチすると
   「40%」だが、B から見れば 0.08%
2. **空キーの行が分母に入る。** 正規化後のキーが空の行は未マッチ扱いで分母に残るため、
   キー列が空の行が多いだけでマッチ率が下がる
3. **多対多の重複を反映しない。** 1 行が B の 100 行にマッチしてもカウントは 1。
   マッチ率と出力行数は連動せず、40% でも上限(50 万行)に当たりうる
4. **正規化の成否とデータの重なりを分離できない。** 正規化後の完全一致のみを見るため、
   マッチ率の低下が「データが入れ替わった」のか「キー列の意味が変わった」のか判別できない

### 2-2. 追加する指標

いずれも既存のキー照合処理にほぼ乗るため計算コストは小さい。

| 指標 | 検出できること |
| --- | --- |
| **両側カバー率** | 上記 1 の非対称性。`matchedBKeys` は完全外部結合用に既に構築済みで、統計には未使用。**算出は常に両側、解釈は型ごと**(§1-3) |
| **キーの識別力**(相異なる正規化キー数 ÷ 行数) | キー列が実質機能していない状態(1000 行で 5 種類しかない等) |
| **正規化の寄与**(`exact` でのマッチ率との差分) | 正規化エンジンが実際にどれだけ効いたか。キー照合を 2 回するだけで出る |
| **正規化の潰れ具合**(相異なる生キー → 相異なる正規化キー) | 正規化のやりすぎ。別物を同一視して見かけのマッチ率が上がる事故 |
| **多重度プロファイル**(1:1 / 1:N / N:M の分布) | キー選択の失敗。平均 50 件マッチならその結合はほぼ無意味 |

**正規化の寄与**は品質指標であると同時に、本製品の差別化(表記ゆれ吸収)を
定量化した数字そのものになる(「3% → 40% に向上」)。

### 2-3. 測れないこと

**正解データが無い限り、マッチが正しいかは測れない。**
別地点なのに正規化後の住所が一致した誤マッチは、上記すべての指標で「成功」と数えられる。
カバー率を上げる改良が誤マッチを増やしているだけ、という事態を検出できない。

教師データ無しでの現実的な緩和策は、**キー以外の列による検算**である。
シードデータの避難所一覧・店舗データはいずれも緯度経度を持つため、
住所でマッチした行の座標が大きく離れていればその一致は疑わしい、と判定できる。
座標距離・施設名の類似度・電話番号の一致など、使える列があれば
カバー率とは独立した精度の推定値が得られる。

### 2-4. 相性チェック — 指標の置き場所(FULL OUTER の使い道)

上記の指標群は、マージ結果に付随する統計として持つと「**やってしまった後の成績表**」になり、
判断に使えない。そこで**マージ前に走らせる独立した診断機能**として切り出す。

機能名は **「相性チェック」**(内部的には affinity)に**確定**。
「相性」は説明不要で通じ、断定的すぎない語感が「あくまで事前の目安」という性質にも合う。

**起動場所は、まずマージウィザードの 1 ステップとして組み込む。**
データセット 2 件とキー列を選んだ時点で診断が出れば、判断が必要なその場に情報が出て、
利用者が新しい画面を覚える必要もない。カタログ横断の探索
(「自分のデータと相性の良いデータはどれか」)は後述の署名の事前計算が前提になるため、
独立した画面はその段階で追加する。

- 計算基盤は**完全外部結合**。マッチした対・A のみ・B のみを**すべて見る**唯一の結合であり、
  対称な診断に必要な情報が揃う(§1-2 のとおり、これを公開データセットとして出すことはしない)
- **データセットを作らない**ため安価で、行数爆発の危険もなく、何度でも試せる
- 出力は §2-2 の指標一式 + アンマッチのサンプル

この機能は 3 つの役割を 1 つの計算で兼ねる。

| 用途 | 内容 |
| --- | --- |
| **マージ前の診断** | この 2 つは結合する価値があるか |
| **キー列の推薦** | 候補となるキー列の組を総当たりで診断し、「住所 × 住所 なら 40%、施設名 × 店舗名 なら 5%」と提示する。現状は利用者が勘で選んでいる |
| **自動追従の品質ゲート** | `latest` での再マージ前に相性を測り直し、記録済みの前回値と比較する(§4-2)。ゲートの実体はこの再診断そのもの |

**単一スコアの扱いには注意する。** 「相性スコア」を 1 つの数値にまとめるのはマッチ率と同じ罠であり、
非対称性を隠す。したがって、

- **ランキング用途**(相性の良い順に並べる)には Jaccard ベースの対称な単一値を出す
- ただし**内訳を必ず併記**し、**ゲート判定には単一スコアを使わない**(個別指標で判定する)

> **将来:** 「自分のデータと相性の良いデータセットはどれか」をカタログ全体に問えると探索機能として強いが、
> 全件の CSV を読むのは重い。その場合はデータセットごとに**キーの署名**
> (正規化済みキー集合の MinHash など)を事前計算し、署名同士の比較で Jaccard を推定する。
> 後から足せる最適化であり、最初は 2 データセット間の診断で十分。

### 2-5. 長期的な方向

デジタル庁の推奨データセット仕様では全国地方公共団体コードや施設 ID の付与が求められているが、
実際の自治体データには含まれていないことが多い。本製品は
**47 都道府県 / 1,741 市区町村と団体コードのマスタを同梱している**([`lib/regions.ts`](../../lib/regions.ts))ため、

- 投稿時に「団体コードの列がありません。追加すると他データと結合しやすくなります」と指摘する
- 都道府県・市区町村の列があれば団体コードを自動付与する

といった投稿者への指導が実装できる。ID で結合できるデータが増えれば表記ゆれ正規化に頼る場面が減り、
**マッチ率という指標への依存自体が下がる**。これが最も健全な方向である。

## 3. 来歴(provenance)

### 3-1. 現状の欠落

マージ結果は `sourceType: "MERGED"` の新規 Dataset として保存されるが、来歴は
**日本語の説明文 1 行**にしか残っていない。

```
「鳥取県 避難所一覧」と「山陰データラボ 店舗ポイントデータ」をマージ(キー: 住所 ⇔ 住所、正規化: address、マッチ率: 40.0%)
```

このため以下が成立しない。

- **元データセットへの参照が無い。** ID もリンクも無く、元が削除されれば来歴は完全に消える
- **統計が保存されていない。** マッチ率は API レスポンスとして返るだけで、DB には散文中の文字列としてしか残らない。前回との比較には日本語のパースが必要になる
- **行の由来が不明。** 完全外部結合では片側のみの行が混在するが区別できない
- **列の由来が不明。** 列名が衝突したときだけ接頭辞が付くため、衝突しない列は出所が消える
- **多段の来歴が切れる。** マージ結果を再マージすると連鎖を辿れない

### 3-2. 既知の不具合(要修正)

**マージ結果のライセンスが継承されていない。**
`prisma.dataset.create` が `license` を渡しておらず、スキーマ既定値の `CC-BY-4.0` が
無条件に入る。政府標準利用規約のデータと独自ライセンスのデータをマージしても
出力は「CC-BY-4.0」と表示される。**ライセンスの誤表示**であり、優先的に直す。

**決定した規則:候補を提示したうえで、公開前に人が確定させる。**

1. マージ実行時、判定できる組み合わせは**安全側の候補**を提示する
   (CC-BY 同士 → CC-BY、片方が CC-BY-SA → SA を伝播、CC0 + X → X)
2. 判定できない組み合わせ(独自ライセンス、規約の解釈が分かれるもの)は
   **未確定のまま**にし、両方の出典とライセンスを併記する
3. **未確定のデータセットは公開申請を通さない。** 既存の承認フロー
   (下書き → 承認待ち → 公開)を強制点として使う。下書きのうちは未確定でよい

完全自動決定を採らないのは、「独自ライセンス」など機械判定できないケースで破綻し、
現状と同じ「誤ったライセンス表示」を生むため。逆に一切推定しない案も、
CC-BY 同士のような自明なケースまで毎回手入力になり、面倒から適当な値を
入れられるリスクがある。**推定はするが、公開の関門で必ず人が確認する**形にする。

### 3-3. 記録する項目

| 項目 | 用途 |
| --- | --- |
| 出力 → 入力 2 件の外部キー | 多段の追跡(再帰 CTE で祖先を全取得) |
| 入力の**版**(§4)と内容ハッシュ | 再現性と陳腐化の判定 |
| 入力の**タイトル・ライセンス・組織名の写し** | 元が削除されても来歴が壊れない |
| マージ設定(型・キー列・正規化レベル・結合種別) | 再実行の再現性 |
| 統計(§2 の各指標) | 品質の推移を追える。自動追従の品質ゲートの基準になる |
| 出力列 → 由来データセットの対応 | 列単位の出典。`resolveColumnNames` が既に計算していて捨てている値 |

来歴グラフは**構造上つねに非巡回**である(自分より後に作られたデータセットを親に持てない)。
したがって循環検出は不要で、深さの上限だけ設ければよい。

これが揃うと「この住所は鳥取県庁の避難所一覧(2026-07-20 版、マッチ率 40% で結合)由来」と
根拠つきで返せるようになる。AI エージェント向けにデータを提供する際の前提条件でもある。

## 4. バージョン

### 4-1. 方針

**マージ対象になるデータセットには、明示的な版を持たせる。**
マージ時は「特定の版にピン留め」か「latest(自動追従)」のどちらかを選ぶ。

内容ハッシュによる陳腐化検出だけでは「変わったこと」しか分からないが、
版を保持すれば**過去のマージを実際に再現できる**。
また、自動追従するか否かがマージごとの明示的な選択になる。

### 4-2. ピン留めと latest

| 参照方法 | 出典が更新されたとき | 公開済み出力の扱い |
| --- | --- | --- |
| **ピン留め**(既定) | 何も起きない。「新しい版があります」と通知するのみ。更新は所有者の任意 | 変化しないため利用者への影響なし |
| **latest** | 事前検証 → 品質ゲート通過なら再マージ。失敗・劣化時は直前の版で据え置き、所有者に通知 | 自動反映せず**承認フローに乗せる**(下書き扱い) |

**ピン留めを既定にする。** latest は問題を消すのではなく、選択可能にするだけである。
latest を選んだ場合、以下は依然として起こりうる。

- 新しい版でキー列名が変わり、**再マージ自体が失敗する**
- マッチ率が 40% から 2% に落ちても誰も気づかない
- 公開済み + 従量課金 API の利用者にとって、予告なく中身が変わる

したがって latest には **事前検証・品質ゲート・失敗時のフォールバック(直前の正常な版で据え置き)**
の 3 点が必須。これが無いと、上流の一度の事故で公開中のデータセットが壊れる。

**決定した品質ゲート:**

| 条件 | 判定 |
| --- | --- |
| 新しい版にキー列が存在しない | **即停止**(閾値以前の問題。事前検証で弾く) |
| マッチ率が前回値の **50% を下回る** | 停止して所有者に通知 |
| **累積**で、初回マージ時の値の 50% を下回る | 停止して所有者に通知(下記) |
| 元データが 100 行未満 | 相対判定を使わず**通知のみ**(1 行の増減が数ポイント動きノイズが大きい) |

停止は「自動適用せず所有者に知らせる」であって障害ではない。
**停止のコストは通知 1 件、見逃しのコストは誤ったデータの公開**であり、コストが非対称である。

> **累積判定を併用する理由。** 前回値との比較だけだと、40% → 30% → 22% → 16% のように
> 毎回 50% は割らずに**徐々に劣化する経路を素通りしてしまう**。初回マージ時の値を基準線として
> 保持し、そこからの累積低下も見ることで、閾値を緩めたまま緩慢な劣化を捕まえられる。
> 基準線は来歴レコード(§3-3)に統計を保存していれば追加コストなしで得られる。

閾値は実データを見て調整する前提の初期値である。

多段の伝播もこの方式なら自然に解ける。A→B→C で A が更新されると B が陳腐化し、
B を再実行した時点で C が陳腐化する。トポロジカルソートを事前に組む必要がない。

### 4-3. 版の識別子と表示

**識別子は登録順の連番**(第 1 版、第 2 版 …)。同日に複数回更新しても衝突せず、
ピン留めの参照先として堅牢である。

**表示は「第 3 版(2026-08-13)」**のように登録日を併記し、人が選びやすくする。

**「データの基準日」は独立したメタデータ項目として別に持つ。**
2025 年の調査データを 2026 年に登録することは普通にあり、
登録日を版の識別子に使うと「いつのデータか」と「いつ登録されたか」が混同されるため。

### 4-4. 保持ポリシー

**参照されている版は無期限保持し、それ以外は直近 5 版を残す。**

更新頻度の選択肢に「日次」がある以上、年 365 版になるデータセットが出る一方、
Supabase の無料枠は 1GB である。ただし**ピン留めされた版は削除できない**
(参照が壊れるため)。したがって「古い順に N 個残す」では不十分で、
参照の有無が第一条件になる。

> 5 版という数字は根拠が薄い初期値であり、実データの容量を見てから調整する。

### 4-5. 残る課題

- **再計算の実行基盤。** 再マージは最大 50 万行と重く、更新リクエスト内での同期実行は
  タイムアウトする。陳腐化フラグ方式なら更新時の処理は「直接の子を陳腐化と印付ける」だけで済み、
  重い再計算は明示的な起動時のみになる

## 5. 外部データソース連携との関係

外部 API / CSV URL からの定期取り込み(#2)は **main にマージ済み**である。
この機能は取得したデータを**既存の CSV ストレージへ上書きで materialize** する設計のため、
本書の前提に直接影響する。**以下はもはや将来の懸念ではなく、現在の状態である。**

- 「出典が更新される」が人手の稀な操作ではなく、**cron による自動かつ高頻度の事象**になる
- 版を持たない現状では、**cron が 1 回走った時点で過去のマージが再現不能になる**
- 保持ポリシー(§4-4)の懸念が仮定ではなく実測の問題になる
- 一方で `SyncRun`(同期実行の履歴)が既にあるため、**同期成功ごとに版を作る**のは自然に接続できる

したがって**バージョン導入(§4)の優先度は、外部連携がマージされた時点で上がっている。**
`SyncMode = SCHEDULED` のデータソースが実際に設定されると、その時点から
過去のマージの再現性が失われ始める。

## 6. 実装順序(案)

1. **マージ型の導入**(項目拡張型 / 共通抽出型。`inner / left / full` の選択を型に置き換える)
2. **指標の拡充**(両側カバー率・識別力・正規化の寄与・多重度。既存の統計計算に相乗り)
3. **相性チェック**(2 の指標をマージ前の独立した診断として切り出す。キー列の推薦もここに載る)
4. **来歴の記録**(モデル追加 + マージ実行時の保存 + **ライセンス継承の不具合修正**)
5. **バージョンの導入**(モデル + ストレージキー変更 + 既存データの移行)
6. **ピン留め / latest とガード**(品質ゲートの実体は 3 の再実行と前回値の比較)
7. **保持ポリシー**(参照されている版を保護した世代管理)
8. **非キー列による精度推定**(座標距離等での検算)

1〜4 は既存構造への追加で完結する。5 は `Dataset` が CSV・列定義・行数を直接持つ構造を
版側へ移す改修になり、**アップロード・ダウンロード・マージ・REST API v1・カタログの
全読み取り経路**に影響する。既存データの移行(現行の 1 件を「初版」として作成)も必要。

3 を先に置いているのは、これが単独で価値を持つ(キー列を勘で選ぶ現状が改善される)一方、
6 の品質ゲートの前提にもなるためである。

## 7. 決定事項と、実装時に確かめること

### 7-1. 決定済み

| 項目 | 決定 | 節 |
| --- | --- | --- |

### 7-2. 実装時に確かめること

数値はいずれも根拠の薄い初期値であり、実データで調整する前提である。

- 保持版数 5 版が容量的に妥当か(Supabase 無料枠 1GB に対して)
- 品質ゲートの 50% と、小規模データを除外する 100 行という境界
- 相性チェックのキー列総当たりが、列数の多いデータセットで実用的な速度に収まるか
- 再計算の実行基盤(§4-5)。Vercel の関数制限内に収める方法
