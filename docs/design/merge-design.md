# マージ設計メモ — マージ型・品質指標・来歴・バージョン

最終更新: 2026-08-13 / 状態: **設計検討中(未実装)**

本書は、マージエンジンを「単に 2 つの CSV を結合する機能」から
「**出典を保持したまま、再現可能な形でデータを組み合わせる基盤**」へ拡張するための設計記録である。
実装済みの挙動と、これから決めることを区別して書く。

現在の実装は [`lib/merge/engine.ts`](../../lib/merge/engine.ts) と
[`app/api/merge/execute/route.ts`](../../app/api/merge/execute/route.ts) にある。

---

## 1. マージ型を 2 種に分ける

### 1-1. なぜ分けるか

現在の「マッチ率」は非対称で、A 側を基準にした片側の指標になっている
([engine.ts の matchRate](../../lib/merge/engine.ts))。これは実装の都合ではなく、
**「マージ」という言葉に用途の異なる 2 つが混ざっている**ことに起因する。

- 避難所 20 件に店舗情報を足したい → 知りたいのは A のカバー率だけ。B が 1 万件でも構わない
- 県の施設台帳と民間の施設台帳が同じ集合を指すか確認したい → 両側が対称に重なるべき

同じ指標で両方を説明しようとすると、必ずどちらかで意味をなさなくなる。
そこで**利用者に用途を先に選ばせ、型ごとに既定値と指標を変える**。

### 1-2. 名称

| 型 | 名称 | 利用者に示す問い |
| --- | --- | --- |
| enrichment | **拡充型** | 「手元のデータに、別のデータの項目を足したい」 |
| reconciliation | **照合型** | 「2 つのデータが、同じものを指しているか確かめたい」 |

「拡充」「照合」はいずれも行政文書で日常的に使われる語で、
特に「照合」(名簿照合・台帳照合)は説明なしで通じる。
2 字漢語 + 型で並びが揃うことも選定理由。

> 「拡充」は行を増やす意味にも読めるため、UI では必ず上表の問いを併記する。
> 代替案として「上乗せ型 / 突き合わせ型」(より口語的で直感的だが軽い印象)も検討した。
> **名称は最終確定ではない。** 実装着手前に決めきる。

### 1-3. 型ごとの挙動

| | 拡充型 | 照合型 |
| --- | --- | --- |
| 基準データ | A を明示的に選ばせる | 対等(基準なし) |
| 既定の結合種別 | 左外部結合(A の行は必ず残す) | 完全外部結合 |
| 主指標 | A 側カバー率 | 両側カバー率 + Jaccard 係数 |
| 重要な副指標 | **多重度分布**(1 行が何件にマッチしたか) | 片側カバー率の偏り |
| 参考値(警告にしない) | B 側カバー率(§1-4) | — |
| 想定出力行数 | ほぼ A の行数 | A ∪ B |
| 主な警告 | 多重度が高い(1 行が多数にマッチし行数が膨張) | 片側だけカバー率が極端に低い(集合がずれている) |

結合種別を利用者に直接選ばせるのではなく、**型を選ぶと既定が決まる**形にする
(変更は可能にする)。inner / left / full という語は利用者の語彙ではない。

### 1-4. 指標は両側算出し、解釈を型で変える

カバー率は**型によらず常に両側とも算出する**。型によって変えるのは
「どちらを主指標として前面に出すか」と、**同じ数値をどう解釈するか**である。

拡充型では、参照側(B)が基準側(A)より大きいのが通常であり、
**B 側カバー率が極端に低いことは正常な姿**である
(避難所 20 件に全国マスタを突き合わせれば B 側は 1% 未満になる)。
したがって拡充型では B 側カバー率を参考値として表示するにとどめ、
**警告や品質ゲートの対象にしてはならない**。問題でないものに警告を出すと、
利用者は直す必要のないものを直そうとする。

一方、照合型で片側だけカバー率が極端に低いことは「集合がずれている」という明確な異常である。
**同じ数値が、一方では正常、他方では異常を意味する。**

拡充型で B 側カバー率より重要なのは**多重度**である。1 件の A 行が B の複数行にマッチすると、
出力が膨張するうえ「どの値を採用するのか」が定まらず、拡充という目的そのものが破綻する。

> なお、拡充型で方向(基準側と参照側)が生じること自体は直すべき歪みではなく、
> 「手元のデータを充実させる」という用途に内在する意味論である。
> 現在の実装が居心地悪いのは非対称だからではなく、**方向を宣言しないまま
> 選択順で暗黙に基準を決めている**ためである。型を選ばせて基準を明示すれば、
> 非対称性は解消すべき対象ではなく、宣言された前提になる。
> 対称性が必要なのは照合型であり、そちらには Jaccard を用意する。

## 2. 品質指標

### 2-1. 現在の定義と限界

```
マッチ率 = (B 側に 1 件以上マッチした A の行数) / (A の総行数)
```

限界が 4 つある。

1. **片側のみ。** B 側のカバー率は計算していない。A=20 行・B=10,000 行で 8 行マッチすると
   「40%」だが、B から見れば 0.08%
2. **空キーの行が分母に入る。** 正規化後のキーが空の行は未マッチ扱いで分母に残るため、
   キー列が空の行が多いだけでマッチ率が下がる
3. **多対多の重複を反映しない。** 1 行が B の 100 行にマッチしてもカウントは 1。
   マッチ率と出力行数は連動せず、40% でも上限(50 万行)に当たりうる
4. **正規化の成否とデータの重なりを分離できない。** 正規化後の完全一致のみを見るため、
   マッチ率の低下が「データが入れ替わった」のか「キー列の意味が変わった」のか判別できない

### 2-2. 追加する指標

いずれも既存のキー照合処理にほぼ乗るため計算コストは小さい。

| 指標 | 検出できること |
| --- | --- |
| **両側カバー率** | 上記 1 の非対称性。`matchedBKeys` は完全外部結合用に既に構築済みで、統計には未使用。**算出は常に両側、解釈は型ごと**(§1-4) |
| **キーの識別力**(相異なる正規化キー数 ÷ 行数) | キー列が実質機能していない状態(1000 行で 5 種類しかない等) |
| **正規化の寄与**(`exact` でのマッチ率との差分) | 正規化エンジンが実際にどれだけ効いたか。キー照合を 2 回するだけで出る |
| **正規化の潰れ具合**(相異なる生キー → 相異なる正規化キー) | 正規化のやりすぎ。別物を同一視して見かけのマッチ率が上がる事故 |
| **多重度プロファイル**(1:1 / 1:N / N:M の分布) | キー選択の失敗。平均 50 件マッチならその結合はほぼ無意味 |

**正規化の寄与**は品質指標であると同時に、本製品の差別化(表記ゆれ吸収)を
定量化した数字そのものになる(「3% → 40% に向上」)。

### 2-3. 測れないこと

**正解データが無い限り、マッチが正しいかは測れない。**
別地点なのに正規化後の住所が一致した誤マッチは、上記すべての指標で「成功」と数えられる。
カバー率を上げる改良が誤マッチを増やしているだけ、という事態を検出できない。

教師データ無しでの現実的な緩和策は、**キー以外の列による検算**である。
シードデータの避難所一覧・店舗データはいずれも緯度経度を持つため、
住所でマッチした行の座標が大きく離れていればその一致は疑わしい、と判定できる。
座標距離・施設名の類似度・電話番号の一致など、使える列があれば
カバー率とは独立した精度の推定値が得られる。

### 2-4. 長期的な方向

デジタル庁の推奨データセット仕様では全国地方公共団体コードや施設 ID の付与が求められているが、
実際の自治体データには含まれていないことが多い。本製品は
**47 都道府県 / 1,741 市区町村と団体コードのマスタを同梱している**([`lib/regions.ts`](../../lib/regions.ts))ため、

- 投稿時に「団体コードの列がありません。追加すると他データと結合しやすくなります」と指摘する
- 都道府県・市区町村の列があれば団体コードを自動付与する

といった投稿者への指導が実装できる。ID で結合できるデータが増えれば表記ゆれ正規化に頼る場面が減り、
**マッチ率という指標への依存自体が下がる**。これが最も健全な方向である。

## 3. 来歴(provenance)

### 3-1. 現状の欠落

マージ結果は `sourceType: "MERGED"` の新規 Dataset として保存されるが、来歴は
**日本語の説明文 1 行**にしか残っていない。

```
「鳥取県 避難所一覧」と「山陰データラボ 店舗ポイントデータ」をマージ(キー: 住所 ⇔ 住所、正規化: address、マッチ率: 40.0%)
```

このため以下が成立しない。

- **元データセットへの参照が無い。** ID もリンクも無く、元が削除されれば来歴は完全に消える
- **統計が保存されていない。** マッチ率は API レスポンスとして返るだけで、DB には散文中の文字列としてしか残らない。前回との比較には日本語のパースが必要になる
- **行の由来が不明。** 完全外部結合では片側のみの行が混在するが区別できない
- **列の由来が不明。** 列名が衝突したときだけ接頭辞が付くため、衝突しない列は出所が消える
- **多段の来歴が切れる。** マージ結果を再マージすると連鎖を辿れない

### 3-2. 既知の不具合(要修正)

**マージ結果のライセンスが継承されていない。**
`prisma.dataset.create` が `license` を渡しておらず、スキーマ既定値の `CC-BY-4.0` が
無条件に入る。政府標準利用規約のデータと独自ライセンスのデータをマージしても
出力は「CC-BY-4.0」と表示される。**ライセンスの誤表示**であり、優先的に直す。

自動決定できないケース(独自ライセンス、政府標準利用規約が絡む場合)があるため、
**両方の出典とライセンスを併記し、利用者に確認を促す**のが安全側。
少なくとも既定値を黙って入れる現状より確実に良い。

### 3-3. 記録する項目

| 項目 | 用途 |
| --- | --- |
| 出力 → 入力 2 件の外部キー | 多段の追跡(再帰 CTE で祖先を全取得) |
| 入力の**版**(§4)と内容ハッシュ | 再現性と陳腐化の判定 |
| 入力の**タイトル・ライセンス・組織名の写し** | 元が削除されても来歴が壊れない |
| マージ設定(型・キー列・正規化レベル・結合種別) | 再実行の再現性 |
| 統計(§2 の各指標) | 品質の推移を追える。自動追従の品質ゲートの基準になる |
| 出力列 → 由来データセットの対応 | 列単位の出典。`resolveColumnNames` が既に計算していて捨てている値 |

来歴グラフは**構造上つねに非巡回**である(自分より後に作られたデータセットを親に持てない)。
したがって循環検出は不要で、深さの上限だけ設ければよい。

これが揃うと「この住所は鳥取県庁の避難所一覧(2026-07-20 版、マッチ率 40% で結合)由来」と
根拠つきで返せるようになる。AI エージェント向けにデータを提供する際の前提条件でもある。

## 4. バージョン

### 4-1. 方針

**マージ対象になるデータセットには、明示的な版を持たせる。**
マージ時は「特定の版にピン留め」か「latest(自動追従)」のどちらかを選ぶ。

内容ハッシュによる陳腐化検出だけでは「変わったこと」しか分からないが、
版を保持すれば**過去のマージを実際に再現できる**。
また、自動追従するか否かがマージごとの明示的な選択になる。

### 4-2. ピン留めと latest

| 参照方法 | 出典が更新されたとき | 公開済み出力の扱い |
| --- | --- | --- |
| **ピン留め**(既定) | 何も起きない。「新しい版があります」と通知するのみ。更新は所有者の任意 | 変化しないため利用者への影響なし |
| **latest** | 事前検証 → 品質ゲート通過なら再マージ。失敗・劣化時は直前の版で据え置き、所有者に通知 | 自動反映せず**承認フローに乗せる**(下書き扱い) |

**ピン留めを既定にする。** latest は問題を消すのではなく、選択可能にするだけである。
latest を選んだ場合、以下は依然として起こりうる。

- 新しい版でキー列名が変わり、**再マージ自体が失敗する**
- マッチ率が 40% から 2% に落ちても誰も気づかない
- 公開済み + 従量課金 API の利用者にとって、予告なく中身が変わる

したがって latest には **事前検証・品質ゲート(マッチ率の相対的低下で停止)・
失敗時のフォールバック(直前の正常な版で据え置き)** の 3 点が必須。
これが無いと、上流の一度の事故で公開中のデータセットが壊れる。

多段の伝播もこの方式なら自然に解ける。A→B→C で A が更新されると B が陳腐化し、
B を再実行した時点で C が陳腐化する。トポロジカルソートを事前に組む必要がない。

### 4-3. 残る課題

- **保持ポリシー。** 更新頻度の選択肢に「日次」がある以上、年 365 版になるデータセットが出る。
  Supabase の無料枠は 1GB。さらに**ピン留めされた版は削除できない**(参照が壊れるため)。
  世代管理の規則は「古い順に N 個残す」では不十分で、
  「**参照されている版は常に保持し、それ以外を N 個残す**」になる
- **版の識別子の粒度。** 同日に 2 回更新すると日付ベースの識別子は衝突する。
  識別子は登録順の連番かタイムスタンプにし、
  **「データの基準日」は独立したメタデータ項目として別に持つ**
  (2025 年の調査データを 2026 年に登録することは普通にあり、日付が両義的になる)
- **再計算の実行基盤。** 再マージは最大 50 万行と重く、更新リクエスト内での同期実行は
  タイムアウトする。陳腐化フラグ方式なら更新時の処理は「直接の子を陳腐化と印付ける」だけで済み、
  重い再計算は明示的な起動時のみになる

## 5. 外部データソース連携との関係

`feat/external-data-sources`(外部 API / CSV URL からの定期取り込み)が並行して進行中である。
この機能は取得したデータを**既存の CSV ストレージへ上書きで materialize** する設計のため、
本書の前提に直接影響する。

- 「出典が更新される」が人手の稀な操作ではなく、**cron による自動かつ高頻度の事象**になる
- 版を持たない現状では、**cron が 1 回走った時点で過去のマージが再現不能になる**
- 保持ポリシー(§4-3)の懸念が仮定ではなく実測の問題になる
- 一方で `SyncRun`(同期実行の履歴)が既にあるため、**同期成功ごとに版を作る**のは自然に接続できる

したがって**バージョン導入は外部連携の後追いではなく、なるべく近いタイミングで入れる**必要がある。

## 6. 実装順序(案)

1. **マージ型の導入**(拡充型 / 照合型。既定の結合種別と主指標の切り替え)
2. **指標の拡充**(両側カバー率・識別力・正規化の寄与・多重度。既存の統計計算に相乗り)
3. **来歴の記録**(モデル追加 + マージ実行時の保存 + **ライセンス継承の不具合修正**)
4. **バージョンの導入**(モデル + ストレージキー変更 + 既存データの移行)
5. **ピン留め / latest とガード**(事前検証・品質ゲート・フォールバック)
6. **保持ポリシー**(参照されている版を保護した世代管理)
7. **非キー列による精度推定**(座標距離等での検算)

1〜3 は既存構造への追加で完結する。4 は `Dataset` が CSV・列定義・行数を直接持つ構造を
版側へ移す改修になり、**アップロード・ダウンロード・マージ・REST API v1・カタログの
全読み取り経路**に影響する。既存データの移行(現行の 1 件を「初版」として作成)も必要。
